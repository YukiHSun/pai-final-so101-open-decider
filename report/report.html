自然言語で書くだけで SO-101 を動かす開発キット
― OSS の判断 AI で、生成 AI のコストを下げる ―

Physical AI 応用1講座 最終課題 説明資料 ／ シミュレーター：MuJoCo ／ ロボット：SO-101（6 軸アーム）

1. 背景

Physical AI を学び始めた人にとって、ロボットに「つかんで運ぶ」を成功させるまでの壁は高いです。よく使われるのは、VLA などのロボット用 AI に、お手本データで動きを学習させる方法です。しかしこの方法では、データ集め、GPU での学習、学習時と実行時のカメラ位置の違いの調整などが必要です。筆者も以前、SmolVLA を学習させて持ち上げを試しましたが、5 回とも最後のつかむところでずれて失敗しました。

一方、Claude などの生成 AI は、画像を見て「キューブが指にはさまれているか」を言葉で答えられるようになりました。そこで、動きを「つかむ」「運ぶ」のような意味のあるスキルに分け、AI には次のスキルを選ばせるだけにします。こうすれば、学習なしで、自然言語の説明を書くだけでシミュレーションで成功体験を得られる開発キットを作れると考えました。

ただし、毎ステップの判断まで大きな生成 AI に任せると、呼び出すたびにトークン代と待ち時間がかかります。そこで判断は、選択肢から確率付きで選ぶことに特化した小さな判断 AI（System One 型）に任せます。これまで使ってきた Jev は、高速で安いものの、有料の API で中身も非公開です。2026 年 10 月に、同じ形式で使える判断 AI が OSS として公開されました。これを使えば、API キーも使用料も要らず、自分の PC で判断を回せます。初心者が気軽に試せる開発キットにするために、この OSS の判断 AI を採用できるかを検証しました。

2. 課題の概要（作った開発キット）

MuJoCo 上の SO-101（6 軸アーム）に、2 つの作業をさせました。

  • 持ち上げる：3 cm の赤いキューブを 5 cm 以上持ち上げる
  • 運んで置く：キューブを緑のゴールまで運び、中心から 10 mm 以内に置いて離れる

役割は「目・頭・手」の 3 つに分けました。

役割担当すること
目コーディングエージェント（Claude Code、Codex など）各ステップの 2 視点の画像を見て、「キューブが指にはさまれているか」など 10 項目を yes / no / unclear で答える
頭判断 AI（System One 型）観測とロボットの状態から、次のスキルを確率付きで選ぶ。安全確認（例：「空中で持てているか」）の yes 確率も返す
手プログラム（mink による IK + MuJoCo）選ばれたスキルを毎回同じように実行する。決められた順番以外の動きは拒否する

利用者が書くのは、次の自然言語の文だけです。どれも 1 つのファイル（claude_jev_controller.py の TaskSpec）にまとまっています。

  • 作業の目標（例：「キューブを持ち上げ、運び、緑のゴールの中に置いてから離れる」）
  • 各スキルを選ぶ条件（例：「直前に持ち上げを終えたら、運ぶ前に一度握り直す」）
  • 目の担当に答えさせる質問（例：「キューブはゴールの上にあるか」）
  • 危ないスキルの前に聞く安全確認（例：「置く前に、キューブはゴールの上にあるか」）

キットは Claude Code や Codex などのコーディングエージェントの上で実行します。エージェントがそのまま「目」になって、画像を読み、観測を書き、次のコマンドを実行します。手順はリポジトリの AGENTS.md（Claude Code は CLAUDE.md 経由）に書いてあり、エージェントが自動で読み込みます。利用者は「pick_place を最初から最後まで実行して」と日本語で頼むだけです。生成 AI の API キーを別に用意する必要はありません。今回の実行は Claude Code で行いました。

判断 AI は、URL を 1 つ変えるだけで入れ替えられます（DECIDER_URL）。有料の Jev、strands-decider、H2O-Lightning-4B を同じコードで使えます。

3. スキルの説明

運んで置く作業は、次の 10 個のスキルを上から順に実行します（持ち上げる作業は 1〜4 と 10 の 5 個）。各スキルの動きはプログラムに固定されていて、AI は関節の角度も座標も出しません。AI が順番に合わないスキルを選んだり、確信度が 0.45 未満だったりすると、プログラムはその場で止まります。

スキルプログラムがすること実行前の安全確認（yes 確率 0.60 以上で実行）
1. キューブの上へ
move_above_cube		画像から赤いキューブの位置を求め、開いた指をその 9 cm 上へ動かす—（推定位置が作業範囲の外なら停止）
2. 下ろす
descend		開いた指を、キューブの高さまでまっすぐ下ろす—（指先が 3 mm 以上ずれたら停止）
3. つかむ
close_gripper		指を少しずつ閉じて、キューブを両側からはさむ—（両方の指が触れていなければ停止）
4. 持ち上げる
lift		はさんだまま 6.5 cm 持ち上げ、そのまま保つ「両方の指でしっかりはさめているか」
5. 持ち直す
secure_grasp		持ち上げで緩んだ握りを、空中で少し締め直す「空中で、指の間に持てているか」
6. 運ぶ
transfer		高さを保ったまま、ゴールの上まで水平に動かす—（両方の指で持っていなければ停止）
7. 置く
lower		キューブをゴールの床まで下ろす「キューブがゴールの上にあるか」
8. 離す
release		指を開いて、キューブを放す「キューブがゴールの中の床に置かれているか」
9. 離れる
retreat		指を 6.5 cm 上へ離す—
10. 完了
done		シミュレーター上の物理的な成功条件を確かめて終わる「キューブだけがゴールの中にあり、何も触れていないか」（条件を満たさなければ停止）

4. 目的

このキットの「頭」を、有料の Jev から OSS の判断 AI に置き換えても、同じように作業を成功させられるかを確かめることです。試したのは、2026 年 10 月に公開された次の 3 つです。

  • strands-decider（AWS の研究チーム、Apache-2.0）：2B 版（Qwen3.5 ベース）、E4B 版（Gemma 4 ベース）
  • H2O-Lightning-4B（H2O.ai、Apache-2.0）：公開ベンチマークで Jev と同程度の総合点

どれも自分の PC（Apple Silicon）で動くので、使用料がかからず、データも外に出ません。現実の現場でも、通信が不安定な環境や、データを外に出せない工場などでの利用につながります。

5. 検証の方法

  1. 記録した質問の再送：Jev で実行したときに送った 19 回分の質問を、そのまま各モデルに送りました。比べたのは、Jev と同じスキルを選ぶか、合格ラインを越えるかの 2 点です。内訳は次のとおりです。
    • 持ち上げる・成功：5 回
    • 運んで置く・成功：10 回
    • わざと失敗させた確認：4 回
    各記録の jev_state が送った状態です。
  2. 失敗を伝えたときの安全性：「つかみ損ねた」「ゴールの上にない」など、7 か所で観測を失敗の内容に書き換えました。そのうえで、危ないスキルに進まないかを確かめました。
  3. シミュレーションでの実行：目は Claude、頭は判断 AI として、最初から最後まで動かしました。

合格ラインは、Jev のときと同じにしました。

  • スキル選択の確信度が 0.45 以上
  • 安全確認の yes 確率が 0.60 以上

このどちらかを下回るか、順番に合わないスキルが選ばれたら、プログラムはその場で止まります。

6.2 H2O-Lightning-4B が手順を飛ばした一手と、その原因

H2O-Lightning-4B が Jev と違う選び方をしたのは、運んで置く作業の 5 手目、持ち上げた直後だけでした。Jev は「持ち直す」を選びましたが、H2O-Lightning-4B は「運ぶ」を選びました。シミュレーションで実行したときも、プログラムが順番違いとして拒否し、ここで止まりました。

原因は、AI に渡していた行動説明の文でした。

元の説明

  • 持ち直す：「持ち上げた直後で、空中に持っている。運ぶ前に握り直す」
  • 運ぶ：「しっかり空中に持っていて、ゴールの上にはない。ゴールの上へ運ぶ」

持ち上げた直後の様子は、この両方に当てはまります。「しっかり」持てているかどうかは、画像からは分かりません。

直した説明

  1. 順番の説明に、「1 つずつ順番どおりに進む。目的が済んでいるように見えても、スキルを飛ばさない」と書き足しました。
  2. 「持ち直す」と「運ぶ」を、見た目ではなく、直前に完了したスキルで区別する文にしました。
持ち上げた直後に AI がつけた確率直す前 Jev直す前 H2O直した後 Jev直した後 H2O
「持ち直す」（正しい次の手）0.79〜0.870.0261.000.864
「運ぶ」0.13〜0.210.9490.000.111
記録した質問で合格した手（15 手中）15141515

直した後は、H2O-Lightning-4B も「持ち直す」を選ぶようになりました。Jev の迷い（0.79〜0.87）もなくなりました。19 回分の質問をすべて聞き直しても、ほかの手が悪くなることはありませんでした。

7. 工夫した点

  • 役割を分けて、AI に関節角を出させない構成：AI はスキルを選ぶだけにしました。細かい動きと安全ルール（確信度、安全確認、順番チェック）はプログラム側に固定しています。判断 AI を入れ替えても、危ない動きにならない作りです。
  • 公平な比較の工夫：途中でコードの質問文を変えていたため、Jev に実際に送った状態をそのまま記録から送り直しました。また、応答に入っているモデル名を毎回確かめました。最初は、環境変数の設定ミスで、Jev の列もローカルモデルが答えていました。モデル名を確かめることで、これに気づけました。
  • 失敗のケースもわざと作って確かめる：成功したときの判断だけでなく、失敗の観測を 7 か所で作りました。そこで止まれるかを、全モデルで確かめています。
  • サーバー設定の落とし穴を見つける：H2O-Lightning-4B の配布サーバーは、出荷時の設定のままだと、迷っている yes / no の確率を 0.801 に書き換えて返します。これでは 0.60 の安全確認が効かなくなるので、書き換えなし（SHIM_NOUL_FLOOR=0）で動かしました。
  • 確率の内訳から原因を探す：違った一手で、10 個のスキルそれぞれの確率を比べました。その結果、モデルの性能不足ではなく、説明文のあいまいさが主な原因だと分かりました。説明文は、見た目ではなく「直前のスキル」で区別できる形に直しました。
  • 実行の再現性：MuJoCo と IK は決定的です。毎ステップ、それまでのスキルを最初から再実行し、指先の軌跡が記録と 1e-6 m 以内で一致することを確かめてから進めています。そのため、記録から動画を作り直せます。

8. 考察と反省

  • 無料で自分の PC で動く判断 AI でも、説明文を整えれば、この作業では Jev と同じ結果を出せました。一方で、説明文が少しあいまいなだけで、正しい手の確率が 0.026 まで下がりました。判断 AI に渡す選択肢の説明は、画像からは確かめられない言葉（「しっかり」など）に頼らないことが大事だと分かりました。直したのはプログラムの動きではなく、自然言語の説明文だけです。初心者でも、日本語や英語の文を見直すだけで調整できることは、このキットの強みだと考えます。
  • strands-decider は、はい / いいえの安全確認では成功と失敗をおおむね分けられました（特に E4B 版）。しかし、5〜10 個の選択肢から選ぶ問題では確信度が低くなりました。「次は〇〇でよいか」とスキルごとに聞く形にすれば、使える可能性があります。
  • どの作業も 1 回ずつの成功で、キューブとゴールの位置も 1 通りだけです。成功率や、位置を変えたときの強さは、まだ評価していません。
  • 今回コストを下げられたのは「頭」の部分です。「目」は今も毎ステップ生成 AI（Claude）が画像を読んでいて、まだ自動化もしていません。次は、画像を読む部分を API で呼んでループ全体を自動で回し、繰り返し評価したいと考えています。あわせて、目の担当にも小さな公開モデルを使えるかを試し、全体のコストを下げたいと考えています。また、Codex で目の役を最後まで実行することは、まだ試していません。
  • H2O-Lightning-4B の 1 回の判断は 0.8〜1.4 秒で、Jev（約 0.2 秒）より遅いです。今回のようにスキルを 1 つずつ選ぶ作業では問題になりませんでしたが、速い制御には向きません。

9. AI の利用と再現方法

  • 推論に使った AI：Claude（画像の観測）、Jev / strands-decider 2B・E4B / H2O-Lightning-4B（スキルの判断）。学習は行っていません。
  • コード、各ステップの画像、観測、確率、比較結果は、GitHub リポジトリにまとめています。手順は README を見てください。
  • 動画は、H2O-Lightning-4B で「運んで置く」作業を行ったときの記録から作り直したものです。

使用した外部のもの：strands-labs/robots（SO-101 モデルの読み込み）、strands-labs/strands-decider、h2oai/h2o-lightning-4b と internet-projects/h2o-lightning-mlx（Mac 用サーバー）、MuJoCo、mink。いずれも Apache-2.0 です。Jev は TypeSafe の商用 API です。
